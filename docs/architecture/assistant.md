# Beet-Assistent

Teil der [Architektur](../architecture.md) (Epic #89). KI-Assistent auf Bedrock AgentCore: Agent, Kostengrenzen, Tools über das Gateway, Gedächtnis, Pflanzvorschläge, Tracing und Modellvergleich.

Ein KI-Assistent, der Warnungen erklärt und beim Planen hilft. Vor allem ein Experiment mit Bedrock AgentCore, deshalb mit harten Kostengrenzen von Anfang an.

## Agent (`agents/bed-assistant`, Python 3.13, T-40)

- Antwortsprache: die Sprache der Frage (meist Deutsch); Fehlermeldungen und UI bleiben deutsch.
- Strands Agents mit `BedrockModel` (Claude Haiku 4.5 über das EU-Inference-Profil, `temperature` 0,3, höchstens 1024 Ausgabe-Tokens). Die Modell-ID steht in der Stage-Konfiguration und lässt sich für Vergleiche (T-45) austauschen.
- Einstieg `main.py` → `bed_assistant.app`: `BedrockAgentCoreApp` mit einem Entrypoint. Er prüft der Reihe nach Aufrufer (401), Gruppe (403, zweite Verteidigungslinie nach dem Authorizer), Eingabe (400) und Tageskontingent (429) und streamt erst dann die Antwort.
- Request wie `AssistantRequestSchema` in `packages/contracts/src/api/assistant.ts`: `message` (höchstens 2000 Zeichen, Infra reicht die Konstante als `MAX_INPUT_CHARS` an den Agenten) und optional `bedId` (das Beet, das der User gerade sieht; der Agent liest es selbst über die Tools). Python spiegelt das Schema mit pydantic.
- Antwort als Server-Sent Events (`AssistantEventSchema`): `{"text"}` je Teilstück, am Ende `{"done": true, "remaining": n}`; scheitert das Modell mittendrin, `{"error"}` mit deutscher Meldung. Fehler vor dem Stream kommen als JSON `{"message"}` wie bei den Services. Der Header `X-Quota-Remaining` nennt die übrigen Fragen.
- Der Aufrufer kommt aus dem ID-Token, das die Runtime bereits geprüft hat (Header `Authorization` ist dafür freigegeben); die `userId` ist wie überall `sub`.
- Tools kommen über MCP vom AgentCore Gateway (siehe unten, T-41); der Agent verbindet sich pro Frage mit dem ID-Token des Aufrufers (`MCPClient` von Strands) und schließt die Session nach der Antwort. Pro Frage entsteht ein frischer Agent; den Gesprächsverlauf und die Vorlieben des Users holt er aus AgentCore Memory (siehe „Gedächtnis“, T-44).
- Tooling über uv: ruff (Lint und Format), mypy strict, pytest mit moto für DynamoDB. Die Skripte in `package.json` binden das in Turborepo ein, `pnpm lint/typecheck/test/build` prüfen den Agenten also mit.

## Kostengrenzen

- Tageskontingent je User (Standard 20 Fragen, Tag nach Europe/Berlin) in `Prod-AssistantStateful`: ein Zähler-Item `USER#<sub>` / `DAY#<datum>`, per bedingtem `UpdateItem` hochgezählt, sodass auch parallele Anfragen die Grenze nicht überschreiten. Zähler laufen nach zwei Tagen per TTL ab.
- Höchstens 1024 Ausgabe-Tokens je Modellaufruf, 2000 Zeichen Frage und 6 Tool-Aufrufe je Frage (`maxToolCalls` in der Stage-Konfiguration); weitere Aufrufe lehnt ein Hook (`ToolCallLimit`) mit einer Meldung an das Modell ab. Pflanzvorschläge brauchen höchstens `suggestionRounds` (2) Modellrunden.
- Tool-Aufrufe laufen nacheinander (`SequentialToolExecutor`), nicht parallel: Im Modellvergleich schloss das Gateway die MCP-Session, sobald das Modell mehrere `find_plants` gleichzeitig aufrief. Scheitert das Schließen der Session nach einer Antwort, wird das mit Ursache geloggt, ohne Antwort oder ersten Fehler zu verdecken; der Modellvergleich führt bei Fehlern die ganze Ursachenkette auf.
- Vom Gesprächsverlauf behält der Agent höchstens `historyMessages` (20) Nachrichten im Kontext (Sliding Window); alte Tool-Ergebnisse werden beim Wiederherstellen weggelassen. So wächst eine Frage in einem langen Gespräch nicht beliebig. Vorlieben kommen höchstens fünf pro Frage dazu.
- Zugang nur für die Cognito-Gruppen `ai-testers` und `admins`; Gäste nie.
- AWS-Budget (`Prod-SharedStateful`) für das ganze Konto, 10 USD im Monat, Mails bei 80 % und 100 % der tatsächlichen Kosten an die GitHub-Variable `BUDGET_ALERT_EMAIL`.

## Runtime (`Prod-Assistant`)

- Code-Deployment statt Container: `pnpm --filter @hochbeet/bed-assistant build` legt in `dist/` den Agenten samt aller Abhängigkeiten als Wheels für Linux ARM64 und Python 3.13 ab (rund 80 MB); CDK lädt das als Zip-Asset hoch (`AgentRuntimeArtifact.fromCodeAsset`). So braucht die Pipeline weder Docker noch ECR.
- Eingehend ein JWT-Authorizer auf den Cognito User Pool: Audience ist der SPA-Client, und der Claim `cognito:groups` muss `ai-testers` oder `admins` enthalten (`CONTAINS_ANY`).
- Die Rolle darf genau ein Modell aufrufen (Inference-Profil plus das Modell dahinter in den EU-Regionen) und im Kontingent zählen; keine Marketplace-Rechte. Claude-Modelle muss ein User mit Marketplace-Rechten einmal pro Konto selbst aufrufen, damit Bedrock das Abo anlegt (siehe `docs/deployment.md`).
- Observability: Usage-Logs nach CloudWatch (`/aws/vendedlogs/bedrock-agentcore/<stage>-bed-assistant-usage`); die Ausgaben des Agenten landen im Log der Runtime.
- Tracing (T-47): `tracingEnabled` legt die Trace-Delivery der Runtime an (Delivery-Quelle `TRACES`, Ziel X-Ray, X-Ray-Ressourcen-Policy nur für `delivery.logs.amazonaws.com` und diese Runtime). Voraussetzung ist die X-Ray Transaction Search im Konto (einmalig von Hand, `docs/deployment.md`, Schritt 6), sonst scheitert der Deploy (so in T-40). Spans landen in der Log-Gruppe `aws/spans` und erscheinen unter CloudWatch → *GenAI Observability* → *Bedrock AgentCore*.
  - Instrumentierung: ADOT (`aws-opentelemetry-distro`) im Agenten. `main.py` ruft vor dem Import des Agenten `start_tracing()` (`bed_assistant/telemetry.py`) auf, das wie `opentelemetry-instrument` instrumentiert; so bleibt der Einstiegspunkt `main.py` und das Startskript im Code-Zip ohne festen Interpreterpfad. Aktiv nur mit `TRACING=true` aus der Infra; Tests, Modellvergleich und lokale Läufe bleiben ohne Tracing. `SERVICE_NAME` (`<stage>_bed_assistant`) benennt den Agenten in der Ansicht.
  - Inhalte: Spans zeigen Agent-, Modell- und Tool-Schritte, Dauer, Tool-Namen und Tokens. Strands schwärzt Nachrichten, Systemprompt, Tool-Argumente und -Ergebnisse (`OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_unredacted_attributes=`, also `[REDACTED]`), ADOT erfasst keine Nachrichteninhalte (`OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=false`), Log- und Metrik-Export von ADOT sind aus (die Runtime-Logs gibt es schon). Diese Werte setzt der Agent immer, auch wenn die Runtime andere vorgibt. HTTP-Header (ID-Token, Bearer an das Gateway) erfassen die Instrumentierungen standardmäßig nicht.
  - Kosten: Spans werden als CloudWatch Logs aufgenommen (Standard-Aufnahme, in `eu-central-1` grob 0,6 $ pro GB, plus Speicher), 1 % indexierte Spans sind frei. Eine Frage erzeugt einige Dutzend Spans mit zusammen grob 50 KB; bei 20 Fragen am Tag je Tester und wenigen Testern bleibt das unter 100 MB und damit unter 0,10 € im Monat. Die Aufbewahrung von `aws/spans` legt die Einrichtung fest (empfohlen 30 Tage).
- Aufruf: `POST https://bedrock-agentcore.<region>.amazonaws.com/runtimes/<URL-kodierte ARN>/invocations?qualifier=DEFAULT` mit `Authorization: Bearer <ID-Token>` und einer Session-ID von mindestens 33 Zeichen im Header `X-Amzn-Bedrock-AgentCore-Runtime-Session-Id`. Die ARN steht im SSM-Parameter und als Stack-Output; die Smoke-Tests stellen nach jedem Deploy eine kurze Frage.

## Gateway und Tools (`Prod-Assistant`, T-41)

- AgentCore Gateway `<stage>-bed-assistant-tools` (MCP, Versionen 2025-03-26 und 2025-06-18, ohne semantische Tool-Suche, die Embedding-Kosten hätte). Eingehend derselbe JWT-Authorizer wie die Runtime: ID-Tokens des SPA-Clients mit `ai-testers` oder `admins` in `cognito:groups`.
- Ein Lambda-Target `garden` (`services/assistant-tools`, TypeScript) mit vier nur lesenden Tools, deutsch beschrieben; das Gateway nennt sie `garden___<tool>`:
  - `list_beds`: Beete mit ID, Name und Größe.
  - `get_bed(bedId)`: ein Beet mit allen Pflanzungen, Sorten als Namen, Zeitraum als `from`/`until` und belegter Fläche `area` (Rechteck um die Standfläche, wie die Abstandsregel sie sieht; fehlt bei unbekannter Sorte).
  - `find_plants(query?)`: Sorten des eigenen Katalogs (global, angepasst, eigene) mit Abständen, Familie, Bedarf, Standzeit und Nachbarn als Namen; höchstens 15 Treffer.
  - `evaluate_bed(bedId, week?)`: Hinweise von `evaluateBed()` aus `@hochbeet/garden-rules` mit den deutschen Texten der Regel-Engine.
  Ein- und Ausgaben sind Zod-Schemas in `packages/contracts/src/api/assistant.ts`; die Eingabe-Schemas gehen als JSON Schema in das Target. Fehler (ungültige ID, fremdes Beet, Service nicht erreichbar) kommen als `{ "error": "<deutsche Meldung>" }` zurück, damit der Agent sie erklären kann.
- **Weitergabe der Identität:** Ein Request-Interceptor (Lambda, `passRequestHeaders`) liest bei jedem `tools/call` das bereits geprüfte ID-Token aus `Authorization` und setzt es als Argument `__userToken` in den Aufruf; was das Modell dort angibt, wird überschrieben bzw. entfernt, und das Token erscheint nie im Tool-Schema oder in Logs. Zusätzlich gibt er es als `Authorization`-Header weiter (Rückfallweg, falls das Gateway Header an das Target propagiert). Die Tool-Lambda ruft damit die öffentliche API auf (`https://<domain>/api/garden/…`, `/api/catalog/plants`), genau wie die App: die JWT-Authorizer der Services prüfen das Token, die `userId` kommt weiter nur aus `sub`. Ein User erreicht so über den Agenten nur seine eigenen Beete; ein fremdes Beet ist ein 404.
- Rechte: Das Gateway darf nur die beiden Funktionen aufrufen; die Funktionen haben außer ihren Logs keine AWS-Rechte (kein Tabellen- oder Modellzugriff).
- Smoke-Test nach jedem Deploy: ohne Token 401/403; mit dem Smoke-User `tools/list` und `garden___list_beds` direkt am Gateway, ohne Modellaufruf.

**Abweichung vom Issue (T-41):** Statt eines Rules-Lambda-Targets plus OpenAPI-Targets für die Lese-Endpunkte gibt es ein Lambda-Target für alle vier Tools. OpenAPI-Targets verlangen einen eigenen ausgehenden Credential Provider (API-Key oder OAuth-Client-Credentials) und kennen das User-Token nicht; außerdem gingen die vollen Service-Antworten (alle Felder, IDs statt Namen) ungefiltert an das Modell. Die Lambda bekommt das Token über den Interceptor, ruft dieselben Endpunkte mit dem User-Token auf und liefert knappe, für das Modell aufbereitete Antworten.

## Chat im Editor (T-42)

- Weg vom Browser zur Runtime: über CloudFront auf der eigenen Domain unter `POST /api/assistant/invocations` (`FrontendStack.addAssistantBehavior()`). Eine CloudFront Function (`assistant-rewrite.js`) schreibt den Pfad auf `/runtimes/<URL-kodierte ARN>/invocations?qualifier=DEFAULT` um; andere Pfade und Methoden beantwortet sie mit 404. Origin ist `bedrock-agentcore.<region>.amazonaws.com`, ohne Cache, mit allen Viewer-Headern außer Host (also `Authorization` und die Session-ID), Read-Timeout 60 s für Tool-Aufrufe vor dem ersten Token. Die ARN liest der Frontend-Stack aus SSM.
- Begründung: Same-Origin wie bei den Services, also kein CORS (die Runtime bietet keine CORS-Konfiguration), keine Runtime-URL im Frontend-Build, dieselbe Domain-Logik für App und Smoke-Tests. Die Runtime prüft das ID-Token selbst; CloudFront reicht es nur durch.
- Frontend: Button „Assistent“ in der Editor-Leiste nur für `ai-testers` und `admins` (`canUseAssistant()` in `src/lib/assistant.ts`, Gruppen als `ASSISTANT_GROUPS` in `packages/contracts`, auch von der Stage-Konfiguration genutzt), nie für Gäste. Desktop: Seitenleiste rechts neben dem Beet, die beim Schließen das Gespräch behält; unter `md`: Bottom-Sheet. Beim Öffnen steht der Fokus im Fragefeld; Enter sendet, Umschalt+Enter macht eine neue Zeile.
- `askAssistant()` schickt Frage und `bedId` mit einer Session-ID pro Chat (`X-Amzn-Bedrock-AgentCore-Runtime-Session-Id`) über `useApiStream()` (wie `useApi()`, aber mit dem Response-Stream) und liest die Server-Sent Events gegen `AssistantEventSchema`. Text erscheint Stück für Stück; „Abbrechen“ bricht den Request ab. Nach jeder Antwort zeigt der Chat die übrigen Fragen des Tages. Fehler (403, 429, Abbruch mittendrin) kommen als deutsche Meldung über `apiErrorMessage()`.
- Ein Hinweis unter dem Chat sagt, dass Antworten von einer KI stammen und falsch sein können.
- Mock (`apps/web/src/mocks/assistant.ts`): dieselben Prüfungen wie der Agent (403 ohne Gruppe, 400, 429 über 20 Fragen am Tag, gezählt im `MockStore`), dann eine feste Antwort als SSE in Stücken; so laufen Dev-Server und Playwright ohne AWS.

## Geprüfte Pflanzvorschläge (T-43)

- Der Chat hat den Knopf „Pflanzvorschläge“: Der Request trägt `suggest: true` und die `bedId` (ohne Beet 400). Die Frage im Feld wird zum Wunsch, sonst gilt eine Standardfrage.
- Strukturierte Ausgabe: `SuggestionListSchema` in `packages/contracts` (Sorte als `plantId`, Art, Position in cm, bei Reihen Länge und Richtung, Montag der Pflanzwoche, Begründung; höchstens 6). `pnpm --filter @hochbeet/contracts schemas` exportiert es als JSON Schema nach `agents/bed-assistant/src/bed_assistant/schemas/`; ein Test schlägt fehl, wenn die Datei veraltet ist. Der Agent baut daraus zur Laufzeit sein pydantic-Modell (`schema_model.py`) für Strands' Structured Output, mit Typen, Pflichtfeldern, Enums und Beschreibungen, aber ohne Raster- und Musterprüfung, damit leicht danebenliegende Werte korrigiert statt verworfen werden.
- Prüfschleife im Agent (`suggest.py`): Beet per `get_bed` lesen, Modell schlägt vor, der Code setzt die Vorschläge aufs 5-cm-Raster und auf den Montag und verwirft solche außerhalb des Beets, ohne gültige Sorte oder Datum, dann prüft `evaluate_bed` mit `candidates` (geplante Pflanzungen werden zusammen mit dem Beet bewertet; jede Fundstelle nennt die beteiligten Kandidaten, unbekannte Sorten stehen in `unknownCandidates`). Bleiben Warnungen zu den Vorschlägen, bekommt das Modell sie zurück und überarbeitet, höchstens `suggestionRounds` Runden (Stage-Konfiguration, Standard 2). Danach verbleibende Warnungen nennt die Antwort offen. Die Werkzeuge ruft der Code dabei direkt über die MCP-Session mit dem Token des Users auf, nicht über das Modell.
- Was das Modell sieht (T-48): Das Beet steht im Prompt, mit Größe, Hauptreihenrichtung und den belegten Flächen der Pflanzungen, die ab heute noch im Beet stehen. Als Werkzeug sieht das Modell nur `find_plants` (`tool_filters` des MCP-Clients, `SUGGESTION_TOOLS`); `get_bed` und `evaluate_bed` ruft nur der Code. Konflikte zwischen vorhandenen Pflanzungen soll das Modell ignorieren. Grund: Mit allen Werkzeugen prüfte Haiku Positionen selbst mit `evaluate_bed`, gab wegen bestehender Konflikte im Beet ganz auf und lief bis zum Abbruch der MCP-Session.
- Zeitgrenze: Eine Vorschlagsanfrage dauert höchstens `SUGGESTION_SECONDS` (50 s), unter dem Read-Timeout von CloudFront (60 s). Läuft eine spätere Runde darüber, gilt die zuletzt geprüfte Runde; reicht schon die erste Runde nicht, endet die Anfrage mit einer deutschen Meldung.
- Antwort: erst die Zusammenfassung als `{"text"}`, dann `{"suggestions", "warnings"}`, dann `done`. Eine Vorschlagsanfrage zählt wie eine Frage gegen das Tageskontingent.
- Editor: Vorschläge erscheinen gestrichelt im Beet (`data-testid="suggestion-<n>"`) mit Status der Regel-Engine (`data-status`, berechnet zusammen mit den Pflanzungen, `src/lib/editor/suggestions.ts`), daneben eine Liste mit Begründung. „Übernehmen“ (einzeln oder alle) legt normale Pflanzungen über `commit({ before: null, after })` an, also gespeichert und rückgängig machbar; „Verwerfen“ entfernt die Vorschläge. Nichts wird automatisch gespeichert, Warnungen blockieren das Übernehmen nicht. Die Umwandlung in eine Pflanzung (`candidatePlanting()` in `@hochbeet/garden-rules`) teilen Tool-Lambda und App.
- Mock: `suggest: true` liefert zwei feste Vorschläge für das Beispielbeet der Playwright-Tests.

## Gedächtnis (T-44)

- Eine AgentCore Memory `<stage>_bed_assistant_memory` in `Prod-AssistantStateful` (bleibt beim Löschen des Stacks erhalten); die ID geht per SSM an die Runtime (`MEMORY_ID`). Alle Daten liegen pro User unter dem Actor `sub` aus dem geprüften Token; das Modell kann keinen anderen User angeben.
- **Kurzzeitgedächtnis:** Jede Nachricht einer Unterhaltung wird als Event gespeichert (Strands `AgentCoreMemorySessionManager`), Session ist die Runtime-Session-ID des Chats. Bei der nächsten Frage stellt der Agent den Verlauf wieder her, deshalb versteht er Rückfragen wie „ja“. „Neue Unterhaltung“ im Chat erzeugt eine neue Session-ID, der Agent kennt den alten Verlauf dann nicht mehr. Events laufen nach `ASSISTANT_CONVERSATION_DAYS` (7) Tagen ab, der kürzesten Frist, die AgentCore Memory erlaubt.
- **Langzeitgedächtnis:** Die eingebaute Strategie für Nutzervorlieben (`preferences`) zieht im Hintergrund Vorlieben aus den Events, etwa Abneigungen, Standort oder Sonnenlage, und legt sie unter `/users/<sub>/preferences` ab. Keine Zusammenfassungen oder allgemeinen Fakten. Vor jeder Frage sucht der Session-Manager die passenden Vorlieben (höchstens 5, Relevanz ab 0,3) und stellt sie in `<user_context>` vor die Frage; bei Pflanzvorschlägen stehen sie im Prompt. Vorschlagsrunden selbst werden nicht als Gespräch gespeichert. Vorlieben bleiben, bis der User sie löscht.
- **Profil:** Unter `/profil` sehen Mitglieder von `ai-testers` und `admins` ihre gemerkten Vorlieben und löschen mit „Alles löschen“ (Bestätigung) alle Vorlieben und alle gespeicherten Gespräche. Der Weg ist derselbe wie für Fragen (`POST /api/assistant/invocations`) mit dem Body `{ "memory": "list" }` bzw. `{ "memory": "forget" }` (`AssistantMemoryRequestSchema`); Antworten `AssistantMemoriesResponseSchema` bzw. `AssistantForgetResponseSchema`. Das zählt nicht gegen das Tageskontingent.
- **Trennung der User:** IAM kann bei einer gemeinsamen Runtime-Rolle nicht pro User einschränken; der Code tut es: Jeder Aufruf nutzt Actor und Namespace aus `sub`, und weil die API Namespaces als Präfix filtert, verwirft der Agent alle Datensätze, die nicht genau im Namespace des Users liegen. Tests in `agents/bed-assistant/tests/test_memory.py` und `test_app.py` prüfen, dass ein User nichts von anderen sieht oder löscht.
- **Rechte der Runtime:** auf genau diese Memory `CreateEvent`, `GetEvent`, `ListEvents`, `DeleteEvent`, `ListSessions`, `RetrieveMemoryRecords`, `ListMemoryRecords` und `BatchDeleteMemoryRecords`; keine Rechte an der Memory selbst (Control Plane).
- Ist keine Memory konfiguriert oder die Session-ID ungültig, antwortet der Agent ohne Gedächtnis; die Profil-Anfragen liefern dann 503 mit deutscher Meldung.
- Mock: Der Mock-Assistent merkt sich Aussagen, die mit „Ich“ beginnen, wörtlich als Vorliebe (im `MockStore` pro User) und beantwortet die beiden Profil-Anfragen.
- Smoke-Test nach jedem Deploy: Der Smoke-User listet seine Vorlieben und löscht danach alles, was der Assistent über ihn weiß (auch die Smoke-Frage).
- Kosten: AgentCore Memory rechnet nach Events, gespeicherten Vorlieben und Abrufen ab, jeweils unter 1 USD je Tausend. Bei höchstens 20 Fragen pro User und Tag (einige Events und ein Abruf je Frage) bleibt das bei den wenigen Testern im Bereich von Cent; das Kontingent begrenzt auch diese Kosten.

## Modellvergleich (T-45)

- Testsatz von 20 Fragen mit erwarteten Eigenschaften in `agents/bed-assistant/evaluation/` (`cases.py`), regelbasiert geprüft: genannte Begriffe, genutzte Tools, keine IDs, Deutsch, Länge, bei Vorschlägen „im Beet“ und „ohne verbleibende Warnungen“. Feste Beet-Daten: Das Skript legt als Smoke-User ein Testbeet mit bekannten Fundstellen an (Daten relativ zum Lauf) und löscht es danach.
- Der Lauf nutzt den Agenten-Code selbst (`StrandsResponder` mit Gateway-Tools und denselben Grenzen), nur mit wechselnder Modell-ID (`models.py`: Claude Haiku 4.5 und Amazon Nova Lite). Tokens und Tool-Aufrufe liest ein Beobachter (`observe`) aus den Metriken von Strands; daraus folgen Kosten je Frage nach einer Preisliste mit oberen Schätzwerten.
- Gestartet nur von Hand: Workflow `assistant-eval.yml` (`workflow_dispatch`, Umgebung `prod`) mit der eigenen Rolle `hochbeet-github-assistant-eval` (Bootstrap-Template, nur `bedrock:InvokeModel*` auf die verglichenen Modelle und `ssm:GetParameter` auf die Gateway-URL, die `Prod-Assistant` unter `/hochbeet/<stage>/assistant/gateway-url` ablegt). Der Lauf bricht ab, bevor er 0,90 $ überschreiten könnte.
- Ergebnisse und Empfehlung in `docs/assistant-evaluation.md`.
- **Abweichung vom Issue:** eigenes Skript statt AgentCore Evaluations. Evaluations bewertet Traces der Runtime mit einem Bewertungsmodell; das braucht X-Ray Transaction Search (seit T-47 eingeschaltet, siehe „Runtime“) und kostet je Urteil einen Modellaufruf. Ein Vergleich über die Runtime hätte zudem deren Rolle um ein zweites Modell erweitert.
